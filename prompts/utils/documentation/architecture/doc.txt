<step id="4.1" name="Grouping">

Identify the **primary** `Architecture-style` of the each `Software System` identified in `<workspace_analysis>`. The `Architecture-style` **MUST** be most **relevant** one.
Ground the identified `Architecture-style` in `CLEAN`.
Set the identified `Architecture-style` as the `<architecture_styles>` variable.

Identify the grouping best practices and principles to use for each `Architecture-style` identified in `<architecture_styles>` defined in the `Clean Architecture`.
Ground the identified grouping best practices and principles in `CLEAN`.

For each identified rule, capture the following fields; a rule that omits any field is **not** fully identified and **MUST** be redone:

- **id** — a stable short identifier (e.g. `G1`).
- **name** — the rule's name in the source (e.g. `Screaming Architecture`).
- **source** — the exact document and section it comes from.
- **scope** — which element or grouping level the rule constrains (e.g. `outermost visible group naming`, `ring assignment of a container`, `direction of edges between rings`).
- **priority** — an integer; when two rules apply to the same grouping decision, the rule with the **lower** `priority` value wins. Priorities **MUST** be derived from the source (e.g. `Screaming Architecture` is a top-level concern per Martin, "Screaming Architecture" (2011), and therefore outranks ring naming).
- **verification** — a testable statement of the form `"the rule is satisfied when X and would be falsified by Y"`, written so it can be checked against the diagram **without** consulting any derived mapping.

Set the identified rules, with all fields populated, as the `<grouping_best_practices>` variable.

Map the identified `Architecture-style` in the `<architecture_styles>` variable to the identified grouping best practices and principles in the `<grouping_best_practices>` variable for each `Software System` in `<workspace_analysis>`.
Ground the mapping in `CLEAN`.
Set the mapped grouping best practices and principles for each `Software System` in `<workspace_analysis>` as the `<system_grouping_best_practices>` variable.

Map the identified `Grouping Rules` in the `<system_grouping_best_practices>` variable to each `Container` in the `<container_diagrams>` variable for each `Software System` in `<workspace_analysis>`.
Ground the mapping in `CLEAN`.
Set the mapped grouping rules for each `Container` in the `<container_diagrams>` variable as the `<container_groupings>` variable.

Comprehensively analyze the `<workspace_data>` and `<workspace_analysis>` variables, to:

1. Group the elements of each `Container` in the `<container_diagrams>` variable by the grouping rules in the `<container_groupings>` variable. It **MUST** match the grouping rules identified in the `<container_groupings>` variable.
   - Apply all Mermaid best practices and principles for grouping to the `<container_diagrams>` variable.
   - Ground all Mermaid best practices and principles for grouping in `[MMD §Flowcharts]`.

2. Verify that the grouping of the elements of each `Container Diagram` in the `<container_diagrams>` variable matches the grouping best practices in the `<container_groupings>` variable. It **MUST** match the grouping best practices identified in the `<container_groupings>` variable.

Re-assign the grouped diagrams back to the `<system_context_diagrams>` variable, replacing its previous value. Do not create a separate variable for the grouped diagrams.
Re-assign the grouped diagrams back to the `<container_diagrams>` variable, replacing its previous value. Do not create a separate variable for the grouped diagrams.

</step>
